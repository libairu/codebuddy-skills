# Ship — 完整交付流水线

在一次会话内把任务从“开始动手”推进到“可以交付”，并保留清晰的 Git 历史。

## 使用时机

在以下场景优先使用本 skill：

- 用户明确说“做完提交并推送”
- 用户希望“开个分支做这个修改”
- 用户要“改完给我 MR/PR 链接”
- 用户说“ship 这个改动”或“走完整交付流程”

如果用户只要本地提交，不推送，优先使用 `commit`；如果用户只要拆分多个 commit 并推送，优先使用 `commit-split`。

## 默认假设

- **基础分支**：仓库默认分支（通常为 `main` 或 `master`）
- **工作目录**：当前仓库根目录
- **提交语言**：跟随用户当前对话语言
- **分支命名**：优先遵循项目已有规范；无规范时使用 `feat/`、`fix/`、`refactor/`、`chore/` 等前缀
- **推送目标**：远端同名分支，并设置 upstream

## 必须遵守的规则

1. **不要直接在默认分支上开发并提交**，除非用户明确要求。
2. **质量检查不能跳过**：优先运行仓库已有 lint、typecheck、test 或构建检查。
3. **提交必须有语义边界**：改动跨领域时要拆成多个 commit。
4. **不要私自改写历史**：除非用户明确要求，否则不要擅自 `amend`、`rebase`、`force push`。
5. **不要跳过 hooks**：不要使用 `--no-verify`，除非用户明确授权。
6. **不要提交敏感文件**：忽略 `.env`、密钥、构建产物、缓存目录等。

## 执行步骤

### 1. 诊断当前仓库状态

优先并行收集以下信息：

```bash
git status
git branch --show-current
git log -1 --format='%an %ae %s'
git remote -v | head -n 2
```

确认：

- 当前是否已经在特性分支上
- 工作区是否已有未提交改动
- 当前仓库远端是否正常

### 2. 需要时创建分支

如果当前位于默认分支，先创建特性分支。

优先遵循现有 `git-branch` 工作流：

- 同步远端默认分支
- 基于最新远端默认分支创建新分支
- 首次推送时设置 upstream 到远端同名分支

如果当前已经在合适的特性分支上，则直接继续，不重复建分支。

### 3. 实施改动

完成用户请求的代码、配置、脚本或文档修改。优先做最小必要修改，不覆盖无关内容。

### 4. 运行质量门禁

优先运行仓库已有脚本，按以下顺序选择：

1. 项目定义的 lint / format / typecheck / test / build 脚本
2. 若无统一脚本，再按项目技术栈选择最小必要检查
3. 只在用户明确要求跳过时才跳过部分检查，并告知风险

如果检查失败：

- 能快速修复的立即修复再重跑
- 无法安全修复的，暂停并向用户汇报阻塞点

### 5. 拆分并提交

提交前重新查看工作树：

```bash
git status -s
git diff --stat
```

如果改动跨目录、跨模块、跨类型或跨职责，按领域拆成多个 commit。优先复用 `commit-split` 的拆分原则。

逐组提交时：

- 明确列出要暂存的文件
- 为每个 commit 写清晰标题
- 保证每个 commit 可独立理解、独立回滚

### 6. 推送到远端

在所有 commit 成型后再统一推送：

```bash
git push -u origin HEAD
```

如果远端拒绝推送：

- **非快进**：停下并告知用户远端已有更新
- **hook / CI 拒绝**：读取错误信息并修复后重试
- **必须强推**：仅在用户明确要求时使用 `--force-with-lease`

### 7. 输出交付结果

推送成功后，尽量输出：

- 当前分支名
- 关键 commit 的短 SHA 与标题
- 可直接打开的 MR / PR 链接

## 反模式

- 在默认分支上直接提交并推送
- 完全不跑检查就交付
- 把多类无关改动塞进一个 commit
- 推送失败后直接 `git push --force`
- 未经用户同意擅自 rebase 或 amend 历史

## 与其他 skill 的关系

- `git-branch`：负责规范建分支与推送 upstream
- `commit-split`：负责多领域改动的拆分提交
- `commit`：只做本地提交，不负责推送
- `commit-push-staged`：只处理已暂存的局部提交
