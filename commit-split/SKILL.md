# Commit Split — 按领域拆分提交

把当前工作树中的改动拆成**独立可读、独立可回滚**的多个 commit，再按需推送到远端。

## 使用时机

在以下场景优先使用本 skill：

- 用户希望“提交并推送”，但当前改动明显跨越多个模块、包、目录或职责
- 用户明确要求“拆 commit”“分领域提交”“整理后再推上去”
- 工作树同时混有业务代码、文档、配置、依赖更新或重构内容

如果用户只想提交**已经暂存**的文件，优先使用 `commit-push-staged`；如果用户要走“建分支 → 改码 → 检查 → 提交 → 推送”的完整交付链路，优先使用 `ship`。

## 默认假设

- **工作目录**：当前仓库根目录
- **目标分支**：当前分支，不自动切分支
- **提交语言**：跟随用户当前对话语言
- **提交格式**：优先采用 Conventional Commits；若项目已有既定规范，优先遵循项目规范

## 必须遵守的规则

1. **禁止一把梭提交**：除非用户明确要求“全部一起提交”，否则不要直接 `git add -A`。
2. **一个文件只进一个 commit**：同一文件不要在多个 commit 中来回拆分，避免历史难读。
3. **优先保证语义边界**：一个 commit 内的文件必须服务于同一目的。
4. **优先保证回滚边界**：任意单个 commit 回滚后，不应把不相关改动一起带走。
5. **保护工作区安全**：不要把 `.env`、凭证、构建产物、缓存目录纳入提交。
6. **不要用模糊 message**：避免“update”“fix stuff”“各种调整”之类无法表达意图的标题。

## 拆分原则

按以下优先级判断 commit 边界（越靠前越优先）：

1. **包 / 层级边界**：前端、后端、移动端、CLI、文档通常应分开
2. **功能模块边界**：不同 feature、页面、服务、接口不要混在一个 commit
3. **类型边界**：文档、配置、依赖、测试通常独立成 commit
4. **变更性质边界**：`feat`、`fix`、`refactor`、`docs` 不混
5. **影响面边界**：用户可见行为变化与纯内部整理尽量拆开

## 执行步骤

### 1. 盘点工作树

先完整查看当前状态：

```bash
git status -s
git diff --stat
git log --oneline -3
```

读完后先**口头归类**，不要一上来就提交。

### 2. 划分提交分组

基于文件路径、变更内容和依赖关系，产出一组清晰的提交方案，例如：

- `feat(auth): 新增邮箱登录流程`
- `fix(api): 修复订单状态映射`
- `docs: 补充接入说明`

如果改动量很小（例如 1–3 个同领域文件），可直接作为一个 commit；如果改动跨领域明显，应先把分组方案告诉用户。用户已经明确表示“分多个 commit 提交”时，不必重复确认。

### 3. 逐组暂存并提交

按依赖顺序提交：被依赖的基础改动在前，文档或补充说明在后。

逐组执行：

```bash
git add <文件1> <文件2> ...
git commit -F - <<'COMMIT_MSG'
<type>(<scope>): <简洁标题>

<可选 body：说明为什么改、影响面、兼容性>
COMMIT_MSG
```

### 4. 统一推送

全部 commit 成型后再推送一次：

```bash
git push origin HEAD
```

如果远端拒绝推送：

- **非快进**：停下并告知用户远端已有更新，不要擅自强推
- **hook / CI 拒绝**：读错误信息并优先修复，不要 `--no-verify`
- **网络波动**：可有限次数重试，但不要把重试变成无限循环

### 5. 输出结果

简洁汇报每个 commit 的短 SHA、标题和推送结果。

## 反模式

- `git add -A && git commit -m "一堆改动"`
- 把文档、依赖和业务代码混在同一个 commit
- 为了省事把多个无关目录一次性提交
- 推送失败后直接 `git push --force`

## 与其他 skill 的关系

- `ship`：用于完整交付流程，本 skill 只负责“拆分并提交/推送”这一步
- `commit-push-staged`：仅处理已暂存文件，不负责分组
- `git-branch`：当需要先建分支再提交时，先走分支 skill
